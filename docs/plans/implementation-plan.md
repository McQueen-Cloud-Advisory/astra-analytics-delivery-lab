## Implementation and verification approach

- **Independent correctness first:** encode approved FIX-01..05 inputs and expected values separately from generation/transformation code. Implement BR-01..04 and KPI-01..08 against those expectations. Never “fix” an expected answer to match implementation without a supported semantic decision. Agent fixture review remains agent-assisted evidence, not a second human verifier.
- **Reversible slices:** start with the small fixture and scoped resources. Preserve the last good published batch; make retries job-aware and same-input reruns idempotent. Prove a subsequent/correction batch and a rejected/interrupted attempt followed by recovery. Do not overwrite a referenced published batch or mutate unrelated cloud resources.
- **Meaningful automation:** use locked dependencies; schema/config and secret checks; fixture, lifecycle, idempotence, admission and publication tests; relevant dependency review; and supported report-source validation. Run actual credential-free CI and retain its revision/result. Local checks alone do not establish remote CI, BigQuery execution or Desktop behavior.
- **Human host work:** the sole manager performs the approved Desktop open/authentication/refresh/interaction checks using short agent-prepared instructions. Keep source-as-of, simulated business date, batch identity and actual refresh evidence distinct. No claim that generated PBIP files establish behavior, and no new preliminary empty-project-open gate.
- **Cost and effort:** use the envelope's current limits rather than duplicating numerical authority here. Count actual attempts, previews and refreshes; do not hide repeated executions inside one nominal attempt. Check projected/observed workload before running, preserve diagnostics on failure, and pause affected work at a limit. Larger/stress profiles are not default acceptance requirements.

The minimum evidence sequence is initial load, same-input repeat, subsequent/correction handling, one controlled failure-to-recovery sequence, actual CI/security checks, real Desktop proof and final release checks. Combine compatible fixture cases to reduce overhead, but respect the real run/refresh counters. If daily limits require another active demonstration day, schedule it honestly; there is no requirement to keep infrastructure running for 60 days or collect weeks of uptime evidence.

Keep local source/evidence sufficient to reproduce the demonstration after cloud teardown. Project deletion, billing-account alteration or removal of unrelated identities requires its specifically named authority; ordinary lab cleanup does not imply it.
