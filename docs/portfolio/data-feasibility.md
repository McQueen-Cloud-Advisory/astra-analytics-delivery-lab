# Data feasibility for the approved survivors

Version: **v1.0**. Assessed: **2026-09-20 America/Chicago**. Phase 3 selection input under [Gate 2](../gates/gate-2-triage-review.md). This is a bounded public-source review and a recommendation, not an approved data contract or an executed generator test.

**Recommendation:** plan to synthesize the company-specific business events for any of OPP-01, OPP-02 or OPP-04. Use public material where it supplies relevant, attributable evidence or useful reference structure. The two public examples reviewed below do not establish a complete, suitable source for any survivor. This is not an exhaustive claim that suitable public data cannot exist. Creating plausible records does not improve the fictional company's data-readiness score.

## Public sources checked

Checks read official dataset descriptions, the published field lists and selected source schemas; no dataset was downloaded, profiled or restored. Links were checked on the assessment date; mutable GitHub `master` links are discovery references, not pinned implementation inputs.

| Public example | Observed coverage and provenance | Candidate fit and limits |
|---|---|---|
| **UCI Online Retail** | UCI describes actual transactions from a UK retailer in 2010–2011, with invoice, product, quantity, timestamp, price, customer and country fields; cancellation is encoded in the invoice identifier. The listing specifies CC BY 4.0. [Official dataset and field list](https://archive.ics.uci.edu/dataset/352/online+retail) | Could inform a sales-line example. The published fields lack payment allocations, credit-to-original-invoice links, due dates, purchase orders/receipts and ship-by/shipment events. An invoice identifier is not an AR ledger. Adding those facts would make the relevant analytical evidence synthetic; UK retail observations do not establish Harborline behavior. |
| **Microsoft Wide World Importers (WWI)** | Microsoft explicitly describes a fictional wholesaler and supplies sales/purchase data generation procedures. This is a publicly distributed sample with simulated business transactions, not observed wholesaler performance. [Scenario](https://learn.microsoft.com/en-us/sql/samples/wide-world-importers-what-is?view=sql-server-ver17), [generation documentation](https://learn.microsoft.com/en-us/sql/samples/wide-world-importers-generate-data?view=sql-server-ver17) | Useful schema reference across all three candidates. Selected tables contain snapshots, balances and some lifecycle fields; they do not by themselves provide the complete event histories proposed below. Restoring the SQL Server sample adds a runtime/extraction dependency; no such installation has been selected or attempted. |

WWI source inspection found the following, with coverage conclusions limited to these inspected tables:

- **AR:** `CustomerTransactions` has customer/invoice references, transaction amount, outstanding balance and finalization date. A nullable invoice reference and current balance do not establish a complete payment/credit allocation history or an independently reconstructable historical balance. [Microsoft table definition](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/samples/databases/wide-world-importers/wwi-ssdt/wwi-ssdt/Sales/Tables/CustomerTransactions.sql)
- **PO:** purchase headers include an expected delivery date; lines include ordered and received quantities, last receipt date and finalization status. These fields do not expose every promise revision, receipt event or cancellation. Finalized must not be silently interpreted as fully received. [Header definition](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/samples/databases/wide-world-importers/wwi-ssdt/wwi-ssdt/Purchasing/Tables/PurchaseOrders.sql), [line definition](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/samples/databases/wide-world-importers/wwi-ssdt/wwi-ssdt/Purchasing/Tables/PurchaseOrderLines.sql)
- **Ship-by:** sales orders contain expected delivery, backorder and picking fields; lines contain quantity and picked quantity. Those are useful relationships, but picking completion is not shipment departure, and expected delivery is not promised ship-by. The inspected tables do not establish the required OMS–WMS split-shipment event bridge. [Order definition](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/samples/databases/wide-world-importers/wwi-ssdt/wwi-ssdt/Sales/Tables/Orders.sql), [line definition](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/samples/databases/wide-world-importers/wwi-ssdt/wwi-ssdt/Sales/Tables/OrderLines.sql)

Before importing any public material, pin its version/date and content hash, retain attribution and modifications, and review the selected asset's terms. UCI attribution follows its stated CC BY 4.0 terms. WWI's linked repository license is MIT, requiring preservation of the relevant notices for copied material; Microsoft's scenario page also identifies embedded public reference data with separate provenance. Do not assume one code license describes every embedded dataset. [Microsoft repository license](https://raw.githubusercontent.com/microsoft/sql-server-samples/master/license.txt)

## Candidate-specific synthesis burden

These are comparative engineering judgments with low confidence, not observed implementation effort. Exact schemas, event rules, fixture counts and acceptance thresholds are reserved for Gates 4–5. All candidates also require controlled duplicates, late corrections, malformed input and recovery cases; generating a clean static CSV alone would understate effort.

| Candidate | Business events needed where unavailable publicly | Relative synthesis/verification burden | Main unvalidated implication |
|---|---|---|---|
| **OPP-01 — Receivables** | Invoices and due terms; payment and credit allocations; reversals/corrections; open balances and collector references | **Modest to moderate:** one source family, but financial reconciliation needs exact amounts, event chronology, partial settlement and unapplied cash cases. Generating balances directly would evade the hard part. | Assumed settlement/overdue patterns may make the worklist artificially easy. Correct lab aging does not validate actual collectability, collections policy, staff time saved or cash recovery. |
| **OPP-02 — Overdue POs** | PO lines; original/current promise changes; partial receipts, receipt corrections, cancellations/closure and buyer references | **Modest to moderate:** quantity reconciliation and changing commitments introduce more state than a single open-PO extract. Similar overall burden to OPP-01; no measured basis for a large difference. | Synthetic supplier reliability and receipt delays cannot establish real vendor behavior or expediting benefit. Using current promise dates alone can erase historical lateness; cancellation and receipt must remain distinguishable. |
| **OPP-04 — Ship-by exceptions** | OMS commitments/cancellations; WMS pick, pack and shipment events; line-to-shipment splits; DC calendars/cutoffs and event-arrival timing | **Higher:** two simulated source families, cross-system keys, quantity conservation, split fulfillment, chronology and timezone/action-window cases | Perfect generated keys, synchronized systems and convenient arrival times can conceal the main real integration risks. Technical classification accuracy cannot prove supervisors could intervene in time or prevent rework. |

The source review provides no reason to prefer a much more complex candidate simply because it has a public sample. OPP-01 and OPP-02 remain close on lab data feasibility; OPP-04 requires more simulation and review. This is one selection input, not a project-selection decision.

## What the single-person experiment can support

Separate **fictional company economics** from **actual lab burden**. The portfolio's professional labor rates and company volumes are scenario comparisons. The real operator must cover requirements review, access/authentication, human-only host checks, release decisions and ongoing demonstration ownership. Agent work, public-data adaptation, generator development, tests, licenses, cloud use and waiting all remain real costs or dependencies. Actual human hours, agent usage charges and platform cost remain unknown until measured; no automatic AI speedup or free labor assumption is justified.

For data planning, use a hand-auditable fixture first: illustratively 10–30 invoice/order cases, with enough linked events to cover each material rule. A later demonstration profile might contain 10,000–100,000 events over a defined history; this is an illustrative scale range, not a target or authorization. Larger company-scale profiles need a specific performance question and the Gate 4 workload/spending envelope. Semantic realism means consistent relationships and deliberate edge cases; it does not require reproducing a fictional company's entire size. Small-fixture success cannot establish company-scale performance.

The same agent writing the generator and transformations creates a risk of both agreeing on the same error. At Gate 5, define independent hand-calculated expected outcomes for material rules, event-level reconciliation and failure cases before testing. Keep those expected results separate from the generator/production transformation code. Use documented alternative distributions and missing-key/late-arrival cases to challenge comfortable assumptions. A second agent's review is still agent-assisted evidence, not independent human or business validation.

Label future report pages, datasets and evidence as synthetic or mixed provenance as applicable. Distinguish real public fields from generated attributes if combining them. Reproducibility requires a seed, generator/version, date range and profile; none is implemented here. A successful lab can establish calculation correctness, controlled recovery and observed platform behavior. It cannot establish Harborline's actual source quality, operational prevalence, adoption, savings, ROI or production readiness.

[Environment readiness](../environment-readiness.md) still governs access uncertainty. Public data availability does not verify GCP billing/IAM, Power BI licensing/hosting/refresh or availability of the sole human for required checks. Resolve those dependencies through selection/architecture conditions before dependent execution. No architecture, generator, platform resource or report has been built by this review.
