## Proposed business baseline requiring approval

| Rule | Recommendation for this fictional experiment | Consequence |
|---|---|---|
| BR-01 — Commitment | Latest effective, known promise drives today's follow-up; retain the original promise and positive postponement days | An agreed extension can remove a line from today's overdue queue; its original commitment remains visible. No historical supplier-performance claim |
| BR-02 — Deadline | One lab business timezone, `America/New_York`; dates are due through local end of day; calendar days include weekends, with no holiday calendar | A line due today is not overdue. This is a proposed business convention, independent of the GCP region |
| BR-03 — Quantity/closure | Ordered quantity is fixed for this MVP. ## Source schemas

Sources are UTF-8 JSON Lines with explicit schema version `1.0`; no blank lines, duplicate JSON keys, unknown fields or non-finite numbers. Timestamps use UTC RFC3339 with second precision (`...Z`); dates use `YYYY-MM-DD`. Monetary input is integer cents, avoiding floating-point currency ambiguity. All fields are required/non-null unless explicitly marked nullable. The source package contains only fictional identifiers, quantities and prices.

| Contract / grain | Fields and constraints |
|---|---|
| **SRC-01 `po_lines`** — one ordered PO line | `line_id STRING` primary key; `po_id STRING`, `line_number INT64 > 0` unique together; `supplier_id STRING`, `buyer_id STRING`, `sku_id STRING` nonempty; `ordered_at TIMESTAMP`; `source_recorded_at TIMESTAMP >= ordered_at`; `initial_promised_date DATE` no earlier than the local order date; `ordered_qty INT64 > 0`; `unit_price_cents INT64 >= 0`; `currency STRING = USD`; `uom STRING = EA` |
| **SRC-02 `line_events`** — one source event revision | `event_id STRING`, `revision INT64 >= 1` composite primary key; `line_id STRING` references SRC-01; `event_type STRING` = `RECEIPT`, `CANCEL`, or `PROMISE`; `event_at TIMESTAMP`; `source_recorded_at TIMESTAMP >= event_at`; `is_void BOOL`; `quantity INT64 nullable`; `promised_date DATE nullable`; `reason_code STRING nullable` |
| **SRC-03 source manifest** — one immutable submitted package | `schema_version`, `fixture_or_profile`, `generator_version`, `seed` (nullable for hand fixture), `business_as_of TIMESTAMP`, `knowledge_cutoff TIMESTAMP >= business_as_of`, filenames, physical record counts, byte counts, SHA-256 per file and source package hash; all hashes computed on actual bytes after implementation |

For nonvoid events, RECEIPT requires `quantity > 0`, other payload fields null; CANCEL requires `quantity > 0` and `reason_code` in `SUPPLIER_CANCEL`, `BUYER_CANCEL`, `CLOSE_SHORT`, with promise null; PROMISE requires a date no earlier than the line's local order date, quantity/reason null. For void revisions, all payload fields are null. Identifiers are case-sensitive ASCII letters/digits/underscore/hyphen, 1–64 characters; fixture display abbreviations in the expected-results document are not extra fields.

**Implementation limits, not company facts:** numeric fields use decimal integer literals only, with no fractional or exponent notation; validate their original token/range before conversion to a JavaScript Number. Bound `ordered_qty`, event `quantity`, `revision` and `line_number` to **1–1,000,000** when non-null; `unit_price_cents` to **0–100,000,000**. Manifest counts must be nonnegative safe integers within the execution envelope. A line value is therefore at most `10^14` cents, below Node's safe-integer ceiling. Before accumulating quantities or cents, verify the next addition cannot exceed **9,007,199,254,740,991 (`Number.MAX_SAFE_INTEGER`)**; otherwise block with `ARITHMETIC_LIMIT`, never round. Input range violations use the same reason; noninteger/type violations use `INVALID_TYPE`. Validate before arithmetic or BigQuery admission. Store cents as bounded INT64, perform monetary multiplication/summation with exact integer or NUMERIC operations, and convert only the final display amount; decimal floating-point monetary accumulation is prohibited. All fixtures fit these limits.

## Event time, revisions and incremental behavior

1. `event_at` is the business occurrence time; `source_recorded_at` is when the source learned a line/revision; pipeline `ingested_at` is observed arrival time assigned during actual ingestion. They must not be substituted for each other. A batch selects lines recorded through `knowledge_cutoff` and ordered through `business_as_of`, then event revisions known through the knowledge cutoff and effective through business as-of (inclusive). Later-effective records can remain raw without affecting the earlier state. An event recorded before its referenced line was recorded is invalid source chronology.
2. PO lines are immutable. Exact repeated line records are no-ops; a different payload for an existing `line_id` or business key blocks the candidate. Amendments require a future contract change, not a guessed overwrite.
3. An event's `line_id`, `event_type` and `event_at` are immutable across revisions. A revision replaces the quantity/promise payload or voids the event; it is not an extra receipt/cancellation. Revisions start at 1 and are contiguous across the retained source history, with strictly increasing `source_recorded_at`. Revisions can arrive physically out of order; a complete history is required before publication.
4. Deduplicate exact canonical field/value matches for `(event_id, revision)`. A different payload for that same key blocks publication; file order never wins. Select the highest revision known at cutoff for each eligible event. Exclude a winning void. For PROMISE events, take the latest `event_at`, breaking exact-time ties by ascending `event_id` with the greatest ID winning; same-time promises with different dates are retained but treated as a conflict and block publication, so that tiebreak only resolves equivalent values.
5. Reconcile each line's effective event timeline: `received_qty >= 0`, `cancelled_qty >= 0`, and cumulative received + cancelled never exceeds ordered. Violations are rejected, never clamped to zero. Event time cannot precede its order. Apply corrections to their original event position before checking the timeline; a newly invalid timeline blocks the corrected batch.
6. Each input delta is unioned with retained accepted event versions. Recompute affected lines, or all lines at this small scale, and publish a new complete immutable batch. A same source-package hash, cutoff pair and contract version is a no-op; a changed cutoff or corrected source produces a distinct batch. Late events are accepted within retained history; they restate a new batch and never mutate an old one.
7. After raw retention expires, backfill/replay requires the complete pinned source package and event history, not an unsupported partial delta. Rebuild in the work boundary and independently reconcile before publication. Source deletion is represented only by an event void; physical deletion of accepted history is not a business correction.

## Source-to-target and reporting model

All source facts have `provenance_class = SYNTHETIC`. Pipeline metadata adds `source_package_hash`, file/record locator, `ingested_at`, `contract_version`, `attempt_id` and canonical payload hash. A semantic payload hash ignores JSON property order but not field values. Exact hashing/serialization implementation must be documented and tested against fixed examples; hashes supplement event-key reconciliation.

| Logical target | Grain / key | Purpose and relationships |
|---|---|---|
| `work.raw_lines`, `work.raw_event_versions` | Each admitted physical source record plus locator | Preserve duplicate/correction evidence; raw admission is distinct from clean business counting |
| `work.canonical_event_versions` | `(event_id, revision)` | Exact duplicate removal, provenance links to all raw occurrences; validate before selecting effective events |
| `work.rejections` | `(attempt_id, file, record_locator, reason_code)` | Retain sanitized invalid record/reason; invalid physical lines get locators even if IDs cannot be parsed |
| `work.candidate_line_state` | `(candidate_batch_id, line_id)` | Join immutable lines, winning events and current/original commitments; compute receipts, cancellations, remaining, closure and KPI inputs |
| `serving.po_line_snapshot` | `(batch_id, line_id)` | Same validated line state, ready batches only; dimensional attributes inline keep the minimal report at one business grain |
| `serving.event_evidence` | `(batch_id, event_id, revision)` for versions known by cutoff | Retain selected/superseded/void/future-effective markers and original effective times for explaining each line; report filters by pinned batch and line |
| `serving.batch_manifest` | `batch_id` | As-of/cutoff, provenance, source hashes, admitted/canonical/rejected counts, validation result and publication time; immutable once published |

Required `po_line_snapshot` outputs are the SRC-01 line/business/dimension fields, retaining `initial_promised_date` as the original commitment, plus: `batch_id STRING`, `current_promised_date DATE`; `received_qty`, `cancelled_qty`, `remaining_qty`, `promise_slip_days`, `remaining_value_cents`, `overdue_value_cents` as bounded **INT64**; `is_open BOOL`, `is_overdue BOOL`; `days_overdue INT64 nullable` (null only for closed lines); `closure_status STRING` in Open/Received/Cancelled/Closed mixed; `provenance_class STRING = SYNTHETIC`; `business_as_of TIMESTAMP`, `knowledge_cutoff TIMESTAMP`, `published_at TIMESTAMP` and `source_package_hash STRING`. All other fields are non-null. `published_at` is the measured publication instant shared with the manifest, not a synthetic source date. `overdue_value_cents` is zero on non-overdue lines. These outputs are specified without prematurely creating DDL or report metadata.

One batch parameter applies to **every** report import. The business model can use `po_line_snapshot` with supplier/buyer attributes directly and an explicit line-key relationship to event drilldown after batch filtering. Do not aggregate line quantities through the one-to-many event table. `batch_manifest` has exactly one row for the selected batch; enforce that before any business total is shown. The publication transaction inserts all three serving objects' rows for the ready batch atomically; setup creates their tables separately. A failed candidate cannot change the previous ready batch. Failure/rejection diagnostics remain in work/local evidence; the unopened or unrefreshed report cannot magically observe a failed run.

## Quality, evolution and acceptance

Require **zero** missing/extra canonical business keys, conflicting revisions, foreign-key failures, invalid event chronology, unexplained quantity differences or KPI/classification mismatches. Reconcile expected key sets and per-line contributions, not only row counts/grand totals. Compare raw physical counts to the manifest; exact duplicates remain explicitly counted. A failure retains sanitized reason codes and blocks candidate publication; a corrected resubmission must link to the failed attempt. Missing master lines are failures, not an Unknown supplier bucket.

Freeze schema `1.0`; an unknown version/field/type fails admission. Additive changes require an explicitly versioned compatibility decision; semantic/grain changes reopen Gate 5 before use. Technical retention follows the current [execution envelope](../operations/execution-envelope.md), including the shortened experiment when recorded; these contracts create no independent resource lifetime or scale authority. Public/private customer ingestion, automatic outreach, native ERP finalization flags, currency/UOM conversions and historical supplier scoring are N/A for the approved synthetic MVP.

Trace to charter SC-01/02/03/05 and fixtures FIX-01 through FIX-05. Every test remains **Not Run**. This contract's approval is proposed at Gate 5 together with KPI/generator/expected-result versions; an internally consistent synthetic ledger cannot validate real source quality or realized benefit.
